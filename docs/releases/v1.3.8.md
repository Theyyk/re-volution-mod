# RE:volution Mod v1.3.8

`v1.3.8` добавляет персональную последовательную progression для настроенных mob-zones поверх max-contributor foundation из `v1.3.7`.

## Progression chain

Progression строится отдельно для каждого обычного world Location ID.

- В цепочку входят только существующие, заполненные mob-zones этого Location.
- Порядок стадий задаётся возрастающим `mobSlotId`.
- ID не обязаны идти подряд. Например, цепочка `2 -> 5 -> 9` полностью валидна.
- Первый заполненный mobSlot Location открыт игроку автоматически.
- Победа на текущей стадии открывает следующий заполненный mobSlot этого же Location.
- Если следующей стадии нет, progression для этой цепочки считается завершённой.

Геометрия без `location populate` не образует progression stage.

## Кто получает progression credit

Progression credit получает только `max contributor`, уже определяемый runtime из `v1.3.7`:

- учитывается максимальный актуальный effective damage contribution;
- игрок, покинувший зону, теряет contribution через существующий HP rollback и не сохраняет progression claim;
- при точной ничьей остаётся правило `v1.3.7`: выигрывает тот, кто раньше достиг итоговой равной суммы contribution;
- last hit сам по себе не даёт progression credit.

Награды по-прежнему делятся между всеми актуальными участниками пропорционально contribution. Progression winner и reward distribution остаются отдельными понятиями.

## Персональный доступ к стадиям

Физические managed mobs остаются общими и видимыми всем игрокам Realm. Progression при этом персональная.

Если игрок пытается атаковать mob-zone stage, которую он ещё не открыл:

- урон полностью подавляется;
- contribution не создаётся;
- combat pause не запускается;
- игрок получает ограниченное по частоте сообщение о необходимости победить предыдущую стадию.

Это позволяет двум игрокам находиться в одном Realm и иметь разный progression state без создания отдельных физических копий мобов для каждого игрока.

## Mongo persistence

Открытые стадии сохраняются в отдельной коллекции `mob_progression`.

Ключ progression состоит из UUID игрока и world Location ID. Документ хранит:

- `playerUuid`;
- `locationId`;
- `unlockedSlots`.

Unlock выполняется идемпотентно через Mongo `$addToSet`, поэтому повторная победа на уже пройденной стадии не создаёт дубликаты и не пропускает стадии.

Progression не привязана к конкретному Realm 1/2/3: игрок сохраняет открытые mobSlot этой Location между игровыми Realm.

## Совместимость

- Legacy Realm 0 managed mobs без Location/Mob Spawn не участвуют в новой progression и сохраняют прежнюю last-hit reward семантику.
- Custom Location/Mob Spawn, не являющиеся mob-zone ID, не получают progression gate.
- Неизвестная или отсутствующая progression chain fail-open: существующая конфигурация не блокируется случайно.
- `FIXED_POINT`, `RANDOM_AREA`, `ROAMING`, separation, safe-surface, HP rollback, proportional rewards, poison contribution, respawn/unload reset и mob-zone overlay не меняют своей семантики.

## Runtime acceptance

Перед stable release проверить:

1. В одном world Location создать минимум три заполненных mob-zone с разными `mobSlotId`, например 1, 2 и 3.
2. Новый игрок может наносить урон mobSlot 1.
3. Урон по mobSlot 2 и 3 до unlock подавляется и HP не меняется.
4. Убийство mobSlot 1 открывает mobSlot 2 для max contributor.
5. После unlock mobSlot 2 принимает урон, но mobSlot 3 всё ещё закрыт.
6. Убийство mobSlot 2 открывает mobSlot 3.
7. После перезахода/рестарта открытые стадии сохраняются из Mongo.
8. Повторное убийство уже пройденной стадии не перескакивает через следующую и не создаёт дубликаты unlock.
9. Два игрока с разным progression state видят одних и тех же мобов, но locked damage подавляется только для игрока без доступа.
10. В совместном убийстве следующий stage получает только существующий max contributor, независимо от last hit.
11. Проверить точную tie-ситуацию по правилу `v1.3.7`.
12. Проверить отсутствие регрессий reward split, HP rollback, roaming, poison, respawn, unload/load, drops/XP и Realm isolation.
