# v1.3.11 - Location progression, Boss Zone и fast-auto

Этот документ описывает текущий DEV-контракт v1.3.11. Это не stable release gate и не меняет production version metadata.

## Цикл Location

Каждая gameplay Location использует один и тот же порядок:

`mob -> mob -> ... -> Boss Zone -> следующая Location`

- Порядок стадий определяется отсортированными configured `mobSlotId`.
- Обычная mob zone имеет `LocationKind.MOB_ZONE`.
- Boss Zone имеет отдельный явный тип `LocationKind.BOSS_ZONE`.
- Старые сохранённые zone definitions без поля `kind` читаются как `MOB_ZONE`; автоматической миграции обычной зоны в boss не происходит.
- Только первый configured stage первой configured Location открыт игроку по умолчанию.
- Первый stage каждой следующей Location закрыт, пока игрок не завершит Boss Zone предыдущей Location.
- Успешная победа в финальной Boss Zone открывает первый configured stage следующей Location.
- Если следующая Location ещё не настроена, progression заканчивается на текущем доступном контенте без ошибки и без автоматического создания новой Location.
- Автоматическая генерация целых Location из строительных шаблонов не входит в v1.3.11.

Boss Zone является отдельным stage-level доменным типом, а не отдельным видом Minecraft entity. Поэтому конкретный managed mob внутри неё по-прежнему может быть zombie/skeleton, а boss-specific правила будут расширять именно Boss Zone/runtime policy.

Для текущего foundation действует строгий layout contract:

- в Location должна быть ровно одна Boss Zone, чтобы Location могла считаться завершаемой;
- Boss Zone должна быть последним configured progression stage;
- Location без Boss Zone не открывает следующую Location;
- несколько Boss Zone делают layout невалидным для completion;
- Boss Zone не на последнем stage не завершает Location;
- обычный последний `MOB_ZONE` никогда не считается boss автоматически.

Admin-настройка:

- `/stage location setboss <locationId> <mobSlotId>` назначает уже существующую финальную mob zone как Boss Zone;
- `/stage location clearboss <locationId> <mobSlotId>` возвращает её в обычный `MOB_ZONE`;
- назначение второго boss или boss не на финальном configured slot отклоняется;
- создание нового stage после уже назначенной Boss Zone отклоняется;
- геометрия и transition point сохраняются при смене типа зоны;
- `/stage location list [locationId]` показывает `type=NORMAL` или `type=BOSS`.

Foundation специально оставляет отдельную точку расширения для будущих механик без переписывания progression:

- HP босса от количества игроков внутри Boss Zone;
- boss ability/reward после победы;
- per-player ограничения на убийство босса;
- enter/leave runtime hooks;
- отдельные respawn/reset policies.

Эти механики пока не входят в текущий scope.

Межлокационный переход не хранится как поведение конкретного `mobSlot`. `MobProgressionService` определяет порядок и доступ, а transition services используют общий resolver следующего/предыдущего configured stage.

## Способы перехода

Поддерживаются четыре независимых способа:

1. Trigger-zone вокруг stage.
2. Панель перемещения по клавише `L`.
3. Административная команда `/stage teleport <locationId> <mobSlotId> [player]`.
4. Fast-auto после успешного открытия следующего stage.

Обычный progression идёт на следующий configured stage той же Location. Из финальной валидной Boss Zone переход ведёт в первый configured stage следующей Location. Обратный переход с первого stage Location ведёт к Boss Zone предыдущей Location, если предыдущий layout валиден и stage открыт игроку.

Все player travel requests повторно проверяются на сервере. Клиент не может открыть stage или обойти progression через GUI/network packet.

## Trigger auto и fast-auto

Это две разные настройки игрока.

`autoTransitionEnabled` относится только к существующей trigger-zone механике: вход в разрешённую половину boundary ring, сообщение, задержка и переход.

`fastAutoEnabled` относится только к немедленному переходу после нового unlock:

- default: `false`;
- хранится в существующем Mongo document `players` как `fastAutoEnabled`;
- переключается маленькой кнопкой `Fast-auto: ON/OFF` на корневом экране меню `L`;
- GUI только отправляет желаемое значение, источник истины находится на сервере;
- после обычного stage target = следующий configured `mobSlot` той же Location;
- после финальной Boss Zone target = первый configured `mobSlot` следующей Location;
- движение выполняется на следующем server player tick через существующий `StageTransitionService`, включая проверку unlock, transition point и safety;
- выключение fast-auto удаляет pending target;
- revoke/reset не позволяют ранее queued target обойти новое состояние progression.

Отсутствующий/небезопасный transition point не изменяет progression. Fast-auto просто не выполняет teleport и сообщает игроку, что переход недоступен.

## Revoke/reset

Существующий контракт сохраняется:

- `revoke` закрывает указанный stage и более поздние stages текущей Location, затем очищает более поздние Locations;
- `reset` очищает выбранную Location и все последующие;
- reset более поздней Location не делает её первый stage автоматически доступным;
- первая configured Location сохраняет свой default first stage.

## Автоматические проверки

v1.3.11 Test Foundation проверяет:

- distinction между `MOB_ZONE` и `BOSS_ZONE`;
- legacy zone definitions остаются `MOB_ZONE`;
- kind соответствует ID namespace;
- только первая Location открыта по умолчанию;
- ровно одна финальная Boss Zone образует валидный completion layout;
- обычный последний stage не завершает Location;
- boss не на финальном stage не завершает Location;
- несколько boss не завершают Location;
- Boss Zone открывает первый stage следующей Location;
- отсутствие следующей Location безопасно;
- общий next/previous resolver работает через границу Location только через валидную Boss Zone;
- закрытая будущая Location не может открыть свои stages сама;
- orphan unlock более позднего stage не обходит opener Location;
- revoke/reset закрывают последующие Locations;
- fast-auto выключен по умолчанию;
- fast-auto queues только фактически открытый target;
- Boss Zone + fast-auto выбирает первый stage следующей Location;
- OFF очищает pending target;
- revoke инвалидирует queued target до Minecraft movement;
- fast-auto preference переживает пересоздание service через repository;
- network wire contract фиксирует `FastAutoTogglePacket` на discriminator 13;
- architecture guard фиксирует одинаковую server/client регистрацию transport.

Minecraft/Mongo/OpenGL не требуются для service tests.

## Минимальная runtime-проверка

После успешного CI и DEV rollout ручная проверка нужна только для того, что нельзя достоверно доказать pure/JUnit тестом:

- назначение Boss Zone через реальную admin-команду и её отображение в `location list`;
- фактический Minecraft teleport после победы в Boss Zone, когда настроена следующая Location;
- отсутствие collision/runtime-проблемы после перемещения.

Progression, layout validation, access, persistence policy, destination resolution, fast-auto policy и network validation должны доказываться автоматическими тестами до runtime smoke.
