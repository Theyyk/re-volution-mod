# Проверки и выпуск

## Проверки перед публикацией

Сборка `clean build` запускает Gradle `check`: 30 существующих Java regression tasks, 22 новых JUnit-теста и архитектурные guards. Задача `test` выполняет JUnit; отдельные прежние runners остаются доступны по именам, например `runeInventoryRegression` и `guiLayoutRegression`. Последняя проверяет также выбор руны для пробуждения: раскладки разных размеров, границы и промежутки слотов, поиск, другие статусы, неполную коллекцию и максимальные ранги. [Аудит baseline, команды и отчёты JUnit](test-foundation.md).

Для отдельных проверок в PowerShell задайте `JAVA_HOME` для JDK 8:

```powershell
.\gradlew.bat runeInventoryRegression guiLayoutRegression
python .github/scripts/check-release-notes.py v1.3.1
git diff --check
```

Автоматические проверки не заменяют проверку опубликованного JAR в игре. В описании выпуска отдельно указывайте, какие проверки выполнены автоматически и что подтверждено вручную. Не переносите результаты проверки предыдущей версии на новый выпуск без проверки.

## Где хранится документация

- `README.md` — русское описание текущего проекта, установка, ссылка на архив скриншотов и сведения об источниках.
- `docs/` — русские инструкции и справочные материалы, полезные независимо от выпуска.
- `docs/releases/<тег>.md` — русское описание конкретного выпуска.
- `.github/release-notes/<тег>.md` — английское описание для GitHub Releases.

Полная история изменений не дублируется в README. Исторические отчёты сохраняют свои адреса и отмечены в [оглавлении](README.md) как архивные.

## Формат описания релиза

Английский файл сохраняет принятые заголовки:

```markdown
## RE:volution vX.Y.Z

Brief release summary.

### Added

### Fixed

### Other

### Download

**Full Changelog:** [previous...current](https://github.com/Theyyk/re-volution-mod/compare/previous...current)
```

Заполните разделы фактическими изменениями. В загрузках укажите имя JAR, требование одинаковой версии на клиенте и сервере, ссылку на совместимый набор ресурсов и его варианты. Русский файл передаёт те же изменения и ограничения; код, имена файлов и идентификаторы сохраняются.

## Порядок выпуска

1. Подготовьте изменения и оба описания: русское и английское. Согласуйте версию в `build.gradle`, `mcmod.info`, документации и теге.
2. Выполните необходимые проверки и проверьте разницу файлов. Сначала объедините рабочую ветку с `develop` и дождитесь успешной проверки именно её текущего коммита.
3. Перенесите проверенный результат из `develop` в `main`. Создавайте тег только для подготовленного коммита выпуска.
4. Автоматизация проверяет наличие обоих описаний, язык и английские заголовки, собирает JAR и публикует GitHub Release из английского файла. Несовпадение версии тега с версией мода останавливает публикацию.
5. Проверьте фактическое описание на странице GitHub Release, приложенный JAR и его версию. Зафиксируйте результат проверки в игре, если она выполнена.
6. Удаляйте завершённые рабочие ветки после объединения, сохраняя незавершённую работу.

Изменение документации само по себе не требует нового тега или изменения версии мода. Исправленное описание существующего релиза обновляется отдельно от его JAR и тега.

## Проверка структурной миграции

`clean build` запускает все существующие regression-задачи и новую `runeTransportContractRegression` для байтового формата переименованных пакетов. Дополнительные классы `*TestSupport` находятся только в `src/test`: они сохраняют межпакетные проверки, не открывая внутренние production API. JAR должен содержать новые классы, прежние ресурсы и не содержать тесты/старые имена. CI подтверждается по exact HEAD и завершённому upload артефакта; runtime фиксируется отдельно.

## Проверки архитектурного baseline 1.3.1

```powershell
.\gradlew.bat -Dnet.minecraftforge.gradle.check.certs=false clean build
python .github/scripts/check-version-consistency.py
python .github/scripts/check-release-notes.py v1.3.1
python .github/scripts/check-structure.py
python .github/scripts/check-structure.py build/libs/RE-volution-1.3.1.jar
git diff --check
```

На этапе 1.3.1 `check` исполнял 21 Java assertion runner: 16 прежних и 5 новых для Mongo schema, wire bytes, resource/payment actions, combat/reward scope и JSON whitelist. Это standalone main-классы. В baseline v1.3.9 их уже 30; Test Foundation добавляет рядом стандартный JUnit-набор, не заменяя эти задачи.

`architectureCheck` и `architectureGuardRegression` входят в `check`. Они проверяют контракт зависимостей и негативные примеры нарушений. Таблица regression entry points проверяется на пропущенные runners. Fingerprints фиксируют ресурсы; packaged guard дополнительно отвергает отсутствующие/устаревшие классы и тесты в JAR.

CI запускается на всех branch push и PR в `develop`. Подтверждать следует завершённый workflow **текущего SHA**, включая проверку JAR и upload artifact. Ни успешная компиляция, ни прежний зелёный commit не заменяют эту проверку.

## Runtime-проверка 1.3.1

Проверяется именно новый JAR на тестовом мире и копии существующих Mongo-данных. Этот checklist не отмечает проверки выполненными автоматически. Проверка входа Forge/vanilla-клиента без мода исключена из acceptance 1.3.1 отдельным решением проекта; optional-client protocol contract при этом остаётся частью совместимости кода.

1. Запустить выделенный Forge 1.12.2 / 14.23.5.2859 на Java 8: без client-class loading ошибок, с прежними JVM/config ключами и whitelist. Подтвердить одно подключение Mongo на граф сервера и штатную остановку.
2. Подключить клиента с модом: вход/повторный вход, `C`, актуальные балансы и расчёт урона, чтение старых коллекций и legacy-слотов. Проверить admin-команды с разрешением и без него, autocomplete и панель.
3. Проверить покупки x1/x5/x10/x100/all, компенсацию дубликатов, заполнение 26 слотов, пробуждение обоих переходов и оплату. Более высокие ранги и slot enhancements должны сохраняться прежним способом.
4. Проверить случайные усиления и серии x100/autoclicker: корректное списание, sync/pulse, отсутствие накопления очереди. Переключить коллекции: боевой вклад остаётся глобальным, reward bonus следует активной коллекции.
5. Проверить managed mobs: spawn/kill, большие HP/награды, click/poison/rage, радиус 2, отсутствие drops/XP, respawn countdown, chunk unload/load и полное обновление admin-командой.
6. Остановить и повторно запустить сервер с тем же миром/БД: отсутствуют дубликаты/старые entity и двойные подписки, сохранены руны, ранги, усиления, ресурсы и whitelist; transient rage не сохраняется.
7. Отключить/включить существующий resource pack и выполнить reload: gunpowder fallback, восстановление текстур, tooltip, шрифты и resize работают прежним образом. Варианты 64/128 используют те же пути.
8. Если используется integrated server, отдельно подтвердить прежнюю доступность команд/resource API и физическую границу core player/mob persistence. Архитектурный релиз не расширяет его исторически неполный игровой режим.

Фиксировать результат с JAR/SHA, версиями Forge/Java, типом клиента и окружением Mongo. Изменение схемы, экономики или поведения по результатам этой проверки оформляется отдельным явным исправлением, а не скрывается в переносе пакетов.


## Единый DEV-канал

`release.yml` проверяет каждый branch push. Dispatcher из default main запускается
после успешного официального Build and Release, но принимает **только push в
`develop` этого репозитория**. Stable tag (`v*`), main, feature/fix ветки, PR и fork
не отправляют `mod-dev-build`. Код рабочей ветки в привилегированном dispatcher
не исполняется. Передаётся ID source CI run через существующий секрет
`RE_VOLUTION_DOCKER`; отсутствие gameplay JAR означает пропуск downstream chain.
[Правила и regression-проверка](dev-dispatcher.md).

Docker проверяет source run через GitHub API и включает точный загруженный JAR в
неизменяемый image, сохраняя digest, revision, branch и JAR hash. Публикация Client
проверяет обе успешные сборки и обновляет единый DEV manifest. Побеждает наибольшая
пара source `(created_at, run_id)`, независимо от порядка завершения image builds;
перезапуск старого source не обгоняет новый. Номера image build/attempt разрешают
равенство только внутри одного source run. Watermark проверяется под общей
блокировкой публикации.

Рабочая ветка → PR → обычный merge в `develop`, без squash/rebase/force. Для
Test Foundation отдельно зафиксирован старт от stable v1.3.9 и обычный merge
инфраструктурного исправления. Перед merge требуется CI точного head SHA, после
merge — CI нового develop SHA. Инфраструктурное обновление не требует stable tag,
смены gameplay version или production manifest. См. [жизненный цикл DEV](https://github.com/Theyyk/re-volution-client/blob/develop/docs/dev-channel.md)
и [приёмку/откат Docker](https://github.com/Theyyk/re-volution-docker/blob/main/README-Two-Channels.md).
